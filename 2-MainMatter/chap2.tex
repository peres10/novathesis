{
    This chapter examines the current state of software engineering practices and technologies relevant to building 
    a modern platform for the \gls{DI} at \glsxtrshort{NOVA} \gls{FCT}. The goal is to overcome limitations of the legacy system - 
    such as fragmented data, manual workflows, and inefficient comunication - by systematically evaluating contemporary approaches to backend 
    architecutres, data persitence, frontend frameworks, and \glsxtrshort{AI}-assisted devleopment workflows. Particular attention is given to the emerging 
    paradigm of \glsxtrshort{AI}-assisted software development, often described as “Vibe Coding” \cite{figma-vibecoding-2025} which supports rapid prototyping by allowing developers to 
    steer \gls{LLM} through natural-language interactions instead of traditional line-by-line coding.
}

{
    Modern web application stacks are chacterized by a wide range of choices at each layer, from infrastructure and backend services to frontend 
    frameworks and development workflows. In the backend, developers must choose between fully managed \gls{BaaS}
    platforms \cite{acropolium-baas-2024} and 
    custom backends that offer fine-grained control over domain logic, performance, and governance . On the frontend, single-page applications and 
    component-based frameworks (such as React, Angular, or Vue) are commonly combined with RESTful or GraphQL \glsxtrshortpl{API}, enabling decoupled 
    client-server architectures and iterative delivery of new features.
}

{
    Beyond classical architecutres, \glsxtrshort{AI}-assisted developlment tools and practices are reshaping how software is desiged and implemented. Under the “Vibe Coding” 
    paradigm, developers describe desired functionality to an \glsxtrshort{LLM}, which generates and refines code iteratively, prioritizng rapid expermientation and high-level 
    intent over manual code authoring. This approach align with agile or small teams to assemble complex prototypes quickly, though it raises questions about 
    maintainability, security, and auditability in production systems. \cite{devto-vibe-coding-2025}
}

\section{Backend Architectures and \glsxtrshort{BaaS}}
\label{sec:sota_backend}
\ntindex[Template]{}
    {
        The choice of backend architecture directly influences development speed, scalability, operational complexity, and the ability to encode complex business 
        rules such as student seriation and multi-role access control. For this project, two main paradigms are considered: \glsxtrlong{BaaS} solutions, 
        which offer ready-made infrastructure and managed services, and custom backends built with mature frameworks such as Spring Boot and Express.js, 
        which provide full control over domain modeling, integration patterns, and deployment environments. \cite{merixstudio-baas-vs-custom-be-2019}
    }

    {
        \glsxtrshort{BaaS} platforms typically optimize for rapid time-to-market by abstracting away server provisioning, database management, and authentication, making them well-suited 
        for early-stage prototyping and small teams \cite{pointofsaas-baas-2025}. In contrast, custom backends allow tailoring of data models, ownerships of the entire codebase, and fine-grained observability, 
        which becomes critical for institutional applications that must satisfy compliance, long-term maintainability, and integration with existing academic processes.
    }

    \subsection{Supabase (Backend-as-a-Service)}
        {
            Supabase is an open-source \glsxtrshort{BaaS} stack that builds on PostgreSQL and exposes automatically generated REST \glsxtrshortpl{API} through PostgREST \cite{supabase-rest-api-overview}, significantly reducing 
            boilerplate \glsxtrshort{CRUD} implementation effort. By providing an integrated suite of tools - including database, authentication, storage, and real-time capabilities - 
            Supabase enables rapid development cycles while leveraging a relational data model that is compatible with established \glsxtrshort{SQL} tooling and practices. \cite{supabase-2019}
        }

        {
            A central feature of Supabase is its built-in authentication system, which supports user registration, password-based login, magic links, and role-based access 
            control\cite{supabase-auth-overview}, simplifying the enforcement of different permission profiles for students, companies, professors and administrators. \gls{RLS}
            policies can be defined directly at the database level, ensuring that authorization rules are enforced close to the data and cannot be bypassed by misconfigured 
            \glsxtrshort{API} clients.\cite{supabase-rls} For logic that goes beyond standard \glsxtrshort{CRUD} operations - such as orchestrating notification workflows or managing student seriation - Supabase offers 
            serverless “Edge Functions”, typically written in TypeScript or JavaScript, which run in a managed environment near end users to minimize latency. \cite{supabase-edge-functions}
        }

    \subsection{Custom Backend: Spring Boot}
        {
            Spring Boot is a widely adopted framework for building production-grade Java or Kotlin backends and is especially suitable for complex, domain-driven systems 
            that require strict typing, layered architectures, and extensive integration capabilities. Its opinionated configuration model and extensive ecosystem 
            (Spring Data, Spring Security, Spring Cloud) allow developers to structure applications into controllers, services, and repositories, facilitating clear 
            separation of concerns and maintanable domain models. \cite{springboot-docs-3x}
        }

        {
            For academic workflows that must support student ranking algorithms, complex eligibility rules, and auditable decision-making processes, the type safety and 
            testability provided by Spring Boot are particularly advantageous. The framework integrates with \glsxtrshort{JPA} and tools like Hibernate Envers to support automatic 
            auditing of entity changes \cite{springboot-docs-3x, hibernate-envers-43}, which helps track user actions, state transitions, and login-related events - capabilities that are often required for administrative 
            oversight and internal compliance in university environments. 
        }

    \subsection{Custom Backend: Express.js (Node.js)}
        {
            Express.js is a minimalist web framework for Node.js that offers a lightweight and flexible foundation for building HTTP \glsxtrshortpl{API} using JavaScript or TypeScript \cite{express-js} .
            Its event-driven, non-blocking \glsxtrshort{I/O} model allows a single process to handle many concurrent connections efficiently, making it well-suited for notification-heavy 
            workloads \cite{node-js} such as broadcasting “Call for Proposals” or status updates to large groups of students.
        }

        {
            The Node.js ecosystem provides a rich set of libraries for templated email generation and delivery, including tools such as Handlebars or \glsxtrshort{EJS} to render dynamic 
            \glsxtrshort{HTML} email bodies \cite{handlebars-js, ejs-js} for coordinators and administrators. Combined with tasks schedulers or message queues, Express-based backends can orchestrate asynchronous 
            communications and background jobs \cite{node-js}, helping address a key functional gap of legacy systems that rely on manual email workflows and ad hoc templates.
        }

\section{Data Persistence: \glsxtrshort{SQL} vs. \glsxtrshort{NoSQL}}
\label{sec:sota_data_persitance}
\ntindex[Template]{}
    {
        The selection of a data persitance model is a fundamental architectural decision that dictates how the system ensures data integrity, scalability, and retrieval efficiency.
        Given the complex ecosystem of the thesis and interships management, which involves multiple stakeholders (Students, Professors, Companies, Secretariat, etc..) and multi-stage
        lifecycle workflows for academic projects, this section evaluates the trade-offs between Relational (\glsxtrshort{SQL}) and Non-Relational (\glsxtrshort{NoSQL}) databases.
    }

    {
        The choice between \glsxtrshort{SQL} and \glsxtrshort{NoSQL} has complex implications for institutional systems.
        Relational databases prioritize data integrity and consistency through \gls{ACID} compliance, while Non-Relational systems typically follow the 
        \gls{BASE} model, trading immediate consistency for horizontal scalability and schema flexibility. For academic management platforms where ata accuracy are indispensable, 
        this distinction is critical. 
    }

    \subsection{The Relational Model (\glsxtrshort{SQL})}
        {
            Relational databases structure data into tables with predifined schemas, utilizing Foreign Keys to establish strcit realtionships between entities. 
            This approach provides fundamental guarantes about data quality and consistency that are essential for institutional systems.
        }

        \begin{itemize}
            \item {
                Structured Data and Integrity: The academic context requires rigorous data consistency.
                For instance, a Candidacy must strictly link to an existing Student and a valid Proposal.
                The relationa model enforces referentials integrity through primary and foregin key constraints, preventing "orphaned" records - 
                a situtation where a child record references a non-existent parent record. This is particularty critical in the DI management platform, 
                where deleted Companies should not retain active Proposals, and Students cannot be assigned to non-existent projects.
            }
            \item {
                Referential integrity mechanism ensure that every foreign key in a child table corresponds to a valid primary key in the parent table,
                maintaining logical consistency across the entire database. Beyond preventing data anomalies, referential integrity supports cascading
                updates and deletions, ensuring that changes propagate correctly across related entities.
            }
            \item {
                Complex Querying: The platform requires complex join operations to generate views - for examploe, listing all proposals for a specific edition
                filtered by a company's validation status, or retrieveing all students that are candidates to a particular internship. SQL excels at these complex 
                relationships through its mature and optimzed query language, which can efficiently traverse multiple table relationships in a single query.
            }
            \item{
                PostgreSQL: This project will initially utilize PostgreSQL (via Supabase for rapid prototyping). Beyond standard SQL features, PostgreSQL offers support for
                complex data types (JSON/JSONB, arrays, enums) and Stored Procedures. This allows the system to handle semi-structured data - such as
                like flexible feedback forms or email tempalte configurations - while maintaining the benefits of a relational schema for academic entities.
            }
        \end{itemize}

    \subsection{The Non-Relational Model (\glsxtrshort{NoSQL})}
        {
            NoSQL databases (e.g., document stores like MongoDB or key-value systems like Redis) offer schema flexibility and horizontal scalability, often at the cost
            of immediate consistency (ACID properties)
        }
        \begin{itemize}
            \item {
                Flexibility vs Structure: While NoSQL allows for rapid iteration of data models without schema migrations,
                the academic domain is highly structured. 
                Entities such as Users, Editions, Proposals, Companies and Students have well-defined attributes that rarely change dynamically or unexpectedly.
                The governance requirements of an academic instution demand clear, predictable data structures rather than evolving, loosely-typed records.
            }
            \item {
                Consistency Challenges: In workflows like Student Seriation, data consistency is essential. 
                A NoSQL appraoch, which often relies on eventual consistency, could introduce race conditions where a student is assigned to a project that is no longer available or where multiple simulataneous requests lead to conflicting state changes.
                The BASE model prioritises availability and partition tolerance over strict consistency, which is acceptable for read-heavy analytics systems but unsuitable for transactional workloads that require immediate correctness.
            }
        \end{itemize}
