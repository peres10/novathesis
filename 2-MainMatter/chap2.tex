{
    This chapter examines the current state of software engineering practices and technologies relevant to building 
    a modern platform for the \gls{DI} at \glsxtrshort{NOVA} \gls{FCT}. The goal is to overcome limitations of the legacy system - 
    such as fragmented data, manual workflows, and inefficient communication - by evaluating contemporary approaches to backend 
    architectures, data persistence, frontend frameworks, and \glsxtrshort{AI}-assisted development workflows. Particular attention is given to the emerging 
    paradigm of \glsxtrshort{AI}-assisted software development, often described as “\textit{Vibe Coding}” \cite{figma-vibecoding-2025} which supports rapid prototyping by allowing developers to 
    steer \glspl{LLM} through natural-language interactions instead of traditional line-by-line coding.
}

{
    Modern web application stacks are characterized by a wide range of choices at each layer, from infrastructure and backend services to frontend 
    frameworks and development workflows. On the backend, developers must choose between fully managed \gls{BaaS}
    platforms \cite{lertaul-2014-ebaas, dbapi-2025-baas-platform} and 
    custom backends that offer fine-grained control over domain logic, performance, and governance. 
    On the frontend, single-page web applications and 
    component-based frameworks (such as React, Angular, or Vue) are commonly combined with RESTful or GraphQL \glsxtrshortpl{API}, enabling decoupled 
    client-server architectures and iterative delivery of new features.
}

{
    While "\textit{Vibe Coding}" and other \glsxtrshort{AI}-assisted practices promise faster experimentation and reduced
    boilerplate, they also introduce new trade-offs regarding maintainability, security, and auditability in production systems \cite{devto-vibe-coding-2025}. 
}

{
    The remainder of this chapter critically reviews these technologies and architecture choices in light of the requirements
    identified for the new platform.
}

\section{Backend Architectures and \glsxtrshort{BaaS}}
\label{sec:sota_backend}
\ntindex[Template]{}
    {
        The choice of backend architecture directly influences development speed, scalability, operational complexity, and the ability to encode complex business 
        rules such as student seriation and multirole access control. For this project, two main paradigms are considered: \glsxtrlong{BaaS} solutions, 
        which offer ready-made infrastructure and managed services, and custom backends built with mature frameworks such as Spring Boot and Express.js, 
        which provide full control over domain modeling, integration patterns, and deployment environments. \cite{lertaul-2014-ebaas, dbapi-2025-baas-platform}
    }

    {
        \glsxtrshort{BaaS} platforms typically optimize for rapid time-to-market by abstracting away server provisioning, database management, and authentication, making them well-suited 
        for early-stage prototyping and small teams \cite{dbapi-2025-baas-platform}. In contrast, custom backends allow tailoring of data models, ownerships of the entire codebase, and fine-grained observability, 
        which becomes critical for institutional applications that must satisfy compliance, long-term maintainability, and integration with existing academic processes.
    }

    

    \subsection{Supabase (Backend-as-a-Service)}
        {
            Supabase is an open-source \glsxtrshort{BaaS} stack that builds on PostgreSQL and exposes automatically generated REST \glsxtrshortpl{API} through PostgREST \cite{supabase-rest-api-overview}, significantly reducing 
            boilerplate \glsxtrshort{CRUD} implementation effort. By providing an integrated suite of tools - including database, authentication, storage, and real-time capabilities - 
            Supabase enables rapid development cycles while leveraging a relational data model that is compatible with established \glsxtrshort{SQL} tooling and practices. \cite{supabase-2019}
        }

        {
            A central feature of Supabase is its built-in authentication system, which supports user registration, password-based login, magic links, and role-based access 
            control\cite{supabase-auth-overview}, simplifying the enforcement of different permission profiles for students, companies and professors. \gls{RLS}
            policies can be defined directly at the database level, ensuring that authorization rules are enforced close to the data and cannot be bypassed by misconfigured 
            \glsxtrshort{API} clients \cite{supabase-rls}. For logic that goes beyond standard \glsxtrshort{CRUD} operations - such as orchestrating notification workflows or managing student seriation - Supabase offers 
            serverless “Edge Functions”, typically written in TypeScript or JavaScript, which run in a managed environment near end users to minimize latency. \cite{supabase-edge-functions}
        }

    \subsection{Spring Boot (Custom Backend)}
        {
            Spring Boot is a widely adopted framework for building production-grade Java or Kotlin backends and is especially suitable for complex, domain-driven systems 
            that require strict typing, layered architectures, and extensive integration capabilities. Its opinionated configuration model and extensive ecosystem 
            (Spring Data, Spring Security, Spring Cloud) allows developers to structure applications into controllers, services, and repositories, facilitating clear 
            separation of concerns and maintainable domain models. \cite{springboot-docs-3x}
        }

        {
            For academic workflows that must support student ranking algorithms, complex eligibility rules, and auditable decision-making processes, the type safety and 
            testability provided by Spring Boot are particularly advantageous. The framework integrates with \glsxtrshort{JPA} and tools like Hibernate Envers to support automatic 
            auditing of entity changes \cite{springboot-docs-3x, hibernate-envers-43}, which helps track user actions, state transitions, and login-related events - capabilities that are often required for administrative 
            oversight and internal compliance in university environments. 
        }

    \subsection{Node.js and Express (Custom Backend)}
        {
            Express.js is a minimalist web framework for Node.js that offers a lightweight and flexible foundation for building HTTP \glsxtrshortpl{API} using JavaScript or TypeScript \cite{express-js}.
            Its event-driven, non-blocking \glsxtrshort{I/O} model allows a single process to handle many concurrent connections efficiently, making it well-suited for notification-heavy 
            workloads \cite{node-js}.
        }

        {
            The Node.js ecosystem provides a rich set of libraries for templated email generation and delivery, including tools such as Handlebars or \glsxtrshort{EJS} to render dynamic 
            \glsxtrshort{HTML} email bodies \cite{handlebars-js, ejs-js} for coordinators. Combined with tasks schedulers or message queues, Express-based backends can orchestrate asynchronous 
            communications and background jobs \cite{node-js}, helping address a key functional gap of legacy systems that rely on manual email workflows and ad hoc templates.
        }
    
    \subsection*{Summary}

        {
            In summary, Supabase offers a managed, high-velocity environment that is ideal for rapid prototyping, while 
            Spring Boot and Express.js provide greater control over domain logic and integration at the cost of more boilerplate and operational
            responsibility.
            As shown in Table~\ref{tab:backend_framework_comparison}, this project adopts Supabase in the early stages and 
            Spring Boot as the long-term backbone for institutional deployment.
            
        }

\section{Data Persistence: \glsxtrshort{SQL} vs. \glsxtrshort{NoSQL}}
\label{sec:sota_data_persitance}
\ntindex[Template]{}
    {
        The selection of a data persistence model is a fundamental architectural decision that dictates how the system ensures data integrity, scalability, and retrieval efficiency \cite{ali-2019-sql-nosql-bigdata}.
        Given the complex ecosystem of the thesis and internships management, which involves multiple stakeholders (Students, Professors, Companies, Secretariat, etc...) and multi-stage
        lifecycle workflows for academic projects, this section evaluates the trade-offs between Relational (\glsxtrshort{SQL}) and Non-Relational (\glsxtrshort{NoSQL}) databases.
    }

    {
        The choice between \glsxtrshort{SQL} and \glsxtrshort{NoSQL} has complex implications for institutional systems,
        where relational databases typically prioritize data integrity and consistency through \gls{ACID} compliance \cite{datacamp-acid-2025},
        while non-relation systems often follow the \gls{BASE} model, trading immediate consistency for horizontal scalability and schema flexibility \cite{aws-acid-vs-base-2026}.
    }


    \subsection{The Relational Model (\glsxtrshort{SQL})}
        {
            Relational databases structure data into tables with predefined schemas, utilizing Foreign Keys to establish strict relationships between entities \cite{ibm-db2-foreignkey-121}. 
            This approach provides fundamental guarantees about data quality and consistency that are essential for institutional systems.
        }

        \begin{itemize}
            \item {
                Structured Data and Integrity: The academic context requires rigorous data consistency.
                For instance, an Application must strictly link to an existing Student and a valid Proposal.
                The relational model enforces referential integrity through primary and foreign key constraints, preventing "orphaned" records - 
                a situation where a child record references a non-existent parent record \cite{referential-integrity-1990}. This is particularly critical in the \glsxtrshort{DI} management platform, 
                where deleted Companies should not retain active Proposals, and Students cannot be assigned to non-existent projects.
            }
            \item {
                Referential integrity mechanism ensure that every foreign key in a child table corresponds to a valid primary key in the parent table,
                maintaining logical consistency across the entire database. Beyond preventing data anomalies, referential integrity supports cascading
                updates and deletions, ensuring that changes propagate correctly across related entities \cite{ibm-db2-foreignkey-121, referential-integrity-1990}. 
            }
            \item {
                Complex Querying: The platform requires complex join operations to generate views - for example, listing all proposals for a specific edition
                filtered by a company's validation status, or retrieving all students that are candidates to a particular internship. \glsxtrshort{SQL} excels at these complex 
                relationships through its mature and optimized query language, which can efficiently traverse multiple table relationships in a single query \cite{microsoft-sql-joins-2025}.
            }
            \item{
                PostgreSQL: This project will initially utilize PostgreSQL (via Supabase for rapid prototyping). Beyond standard SQL features, PostgreSQL offers support for
                complex data types (\glsxtrshort{JSON}/\glsxtrshort{JSONB}, arrays, enums) and Stored Procedures \cite{postgres-jsonb-docs, postgresql-json-18}. This allows the system to handle semi-structured data - such as
                like flexible feedback forms or email template configurations - while maintaining the benefits of a relational schema for academic entities.
            }
        \end{itemize}

    \subsection{The Non-Relational Model (\glsxtrshort{NoSQL})}
        {
            \glsxtrshort{NoSQL} databases (e.g., document stores like MongoDB or key-value systems like Redis) offer schema flexibility and horizontal scalability, often at the cost
            of immediate consistency (\glsxtrshort{ACID} properties) \cite{ali-2019-sql-nosql-bigdata}.
        }
        \begin{itemize}
            \item {
                Flexibility vs Structure: While \glsxtrshort{NoSQL} allows for rapid iteration of data models without schema migrations,
                the academic domain is highly structured. 
                Entities such as Users, Editions, Proposals, Companies and Students have well-defined attributes that rarely change dynamically or unexpectedly.
                The governance requirements of an academic institution demand clear, predictable data structures rather than evolving, loosely-typed records.
            }
            \item {
                Horizontal Scalability: A key advantage of many \glsxtrshort{NoSQL} systems is the ability to easily scale horizontally across multiple nodes,
                distributing data and load to handle very high traffic volumes or massive datasets.
                This is attractive for large, globally distributed consumer applications, but less critical for an institutional platform whose 
                workload is bounded by the number of students, companies and editions.
                In this context, the added operational complexity of managing a distributed \glsxtrshort{NoSQL} cluster is not justified by the expected scale,
                especially when a single relational database can already handle the anticipated load with proper indexing and tuning.
            }
            \item {
                Consistency Challenges: In workflows like Student Seriation, data consistency is essential. 
                A \glsxtrshort{NoSQL} approach, which often relies on eventual consistency, could introduce race conditions where a student is assigned to a project that is no longer available or where multiple simultaneous requests lead to conflicting state changes.
                The \glsxtrshort{BASE} model prioritizes availability and partition tolerance over strict consistency, which is acceptable for read-heavy analytics systems but unsuitable for transactional workloads that require immediate correctness.
            }
        \end{itemize}

    \subsection*{Summary}
        {
            For the internship and dissertation management platform, the structured nature of the domain, strict consistency requirements, and moderate scale favor a relational \glsxtrshort{SQL} database over a \glsxtrshort{NoSQL}
            solution. Table~\ref{tab:data_persitance_comparison} summarizes the main differences between relational and non-relational models in terms of schema, consistency, integrity, querying, and institutional fit,
            and it motivates the choice of PostgreSQL as the primary data store for this project.
        }
        \begin{table}[H]
            \centering
            \renewcommand{\arraystretch}{1.5} % Matches the breathing room of your other tables
            \label{tab:data_persitance_comparison}
            \begin{tabularx}{\textwidth}{|l|X|X|}
                \hline
                \textbf{Criterion} & \textbf{Relational (SQL)} & \textbf{Non-Relational (NoSQL)}  \\ \hline
                \textbf{Schema Definition} & Rigid/Predefined & Schema-less/Dynamic \\ \hline
                \textbf{Consistency Model} & ACID Compliance & BASE (Eventual) \\ \hline
                \textbf{Data Integrity} & Enforced (Foreign Keys) & Application-level logic \\ \hline
                \textbf{Query Complexity} & Native Relational Joins & Aggregation Pipelines \\ \hline
                \textbf{Scaling Strategy} & Vertical Scaling & Horizontal Partitioning \\ \hline
                \textbf{Institutional Fit} & High (Structured Records) & Low (Consistency Risks) \\ \hline
            \end{tabularx}
            \caption{Comparison of Data Persistence Models}
        \end{table}
        

\section{Frontend Frameworks and User Experience}
\label{sec:sota_frontend}
\ntindex[Template]{}
        {
            The "Outdated \glsxtrfull{UX}" of the legacy system is identified as a critical failure point, particularly for external stakeholders such as companies who
            struggle to register, manage accounts, or monitor proposal status. 
            To address these limitations, the new platform must transition from static, server-rendered pages to
            a modern, reacting \gls{SPA} or hybrid architecture that enables faster navigation, richer interactivity \cite{react-docs-2026}, and consistent interfaces across distinct user roles.
        }

        \subsection{React.js}
            {
                React is a free, open-source JavaScript library maintained by Meta that specializes in building interactive user interfaces through component-based architecture \cite{react-docs-2026}.
                Unlike traditional web development where the entire page must be reloaded on data changes, React efficiently re-renders only the components that have actually changed, 
                using its virtual DOM reconciliation process to minimize performance overhead. React uses \gls{JSX}, a syntax extension that allows developers to write HTML-like code directly
                within JavaScript \cite{react-docs-2026}, making the \glsxtrshort{UI} logic more readable and maintainable.
            }

            {
                React may be selected as the core library for building the platform's user interface for two primary reasons:
            }
            \begin{enumerate}
                \item {
                    Component-Based Architecture: React allows for the creation of reusable, self-contained \glsxtrshort{UI} components
                    (e.g. "ProposalCards" where all the details from a proposal are, that can be used in multiple pages). 
                    This modular approach ensures consistency across the distinct interfaces required for Students, Professors, and Companies, 
                    while enabling efficient code reuse and simplified maintenance.
                }
                \item {
                    Synergy with \glsxtrshort{AI}-Assisted Development: The project methodology relies on \textit{Vibe Coding} tools for rapid prototyping.
                    Tools such as Lovable, Bolt.new, Figma Make and Google AI Studio are optimized to generate code specifically for the React ecosystem.
                    Using React ensures  that the code generated during the prototyping phase is immediately usable and extensible, eliminating the need for
                    time-consuming library migrations.
                }
            \end{enumerate}

            {
                In addition, React integrates naturally with full-stack frameworks like Next.js, which can provide \gls{SSR}, \gls{SSG}, and routing natively when needed,
                without changing the underlying component model \cite{next-js, nextjs-app-router, strapi-ssr-vs-ssg-next-js}. 
                This means that if later iterations require improved performance for specific pages, the existing React components can be hosted
                within a Next.js application with minimal refactoring, preserving the benefits of the initial AI-assisted prototyping workflow.
            }

        \subsection{Angular}
            {
                Angular is a full-featured, opinionated frontend framework maintained by Google that provides an integrated solution for components,
                routing, forms, and state management in a single toolkit. 
                Unlike React, which focuses on the view layer and relies on additional libraries for concerns such as routing, Angular ships with a more
                prescriptive structure (modules, services, dependency injection), which can be advantageous for large teams that value strong conventions.
            }

            {
                Angular was considered as a viable alternative because if offers:
            }
            \begin{itemize}
                \item {Strong typing when used with TypeScript by default}
                \item {Built-in patterns for modularization and dependency injection}
                \item {Mature tooling for forms, validation, and reactive programming}
            \end{itemize}

        \subsection*{Summary}
            {
                In summary, the platform will adopt a React-based frontend because it combines flexible component model, 
                strong tool support, and excellent compatibility with \glsxtrshort{AI}-assisted "\textit{Vibe Coding}" workflows, while
                still allowing future adoption of frameworks like Next.js for \glsxtrshort{SSR} or \glsxtrshort{SSG} if needed. 
                Angular remains a robust alternative for institutional systems, but in this context its more opinionated structure and weaker
                alignment with current \textit{Vibe Coding} tools make it less suitable, as reflected in the comparison of frontend technologies
                in Table~\ref{tab:frontend_framework_comparison}.
                In the next section, the discussion of \glsxtrshort{AI}-assisted development will also show that React is the predominant target stack of the
                \textit{Vibe Coding} tools considered for this project, further reinforcing its choice.
            }

\section{AI-Assisted Development \textit{(Vibe Coding)}}
\label{sec:sota_ai_assited_dev}
    {
        Traditional software development involves writing code manually, line by line, or using code assistants that give fragments of code in the developer's \glsxtrshort{IDE}, such as
        GitHub Copilot, Claude, or Gemini-based CLI tools.
        \textit{Vibe Coding} tools differ from these assistants because instead of focusing on line-level code completion, they provide an integrated environment where 
        a \glsxtrfullpl{LLM} generates and iteratively refines entire screens, workflows, or even full-stack applications through natural language instructions, with live preview and project-level context \cite{cloudflare-vibecoding-2025,devto-vibe-coding-2025}.
        For this reason, the dissertation concentrates on \textit{Vibe Coding} tools specifically designed for the \glsxtrshort{UI} and application scaffolding with immediate visual feedback - namely
        Lovable, Bolt.new, and Figma Make - rather than on generic code completion tools.
        This section analyzes the capabilities of such tools to determine their viability for the rapid prototyping phase of this project.
    }       
            
    \subsection{Analysis of Vibe Coding Tools}
        {
            For this dissertation, there representative \textit{Vibe Coding} tools were considered and explored: \textbf{Lovable, Bolt.new, } and \textbf{Figma Make}.
            They differ in scope (full-stack vs. frontend-centric), integration with existing workflows, and the amount of control they give developers over the generated code. 
        }

        \subsubsection*{Lovable}
            { 
                    Lovable focuses on providing an end-to-end environment for building web applications with minimal friction. 
                    From a single interface, it can generate React-based \glsxtrshortpl{UI}, configure Supabase-backed database and backend,
                    and deploy the resulting application.
                    When requirements are underspecified, Lovable scaffolds the missing pieces on both frontend and backend, and offers automatic debugging
                    and safety checks that make it forgiving for users with limited programming experience. A distinctive advantage is bidirectional GitHub
                    synchronization: projects can be edited in an external \glsxtrshortpl{IDE} and then synced back to Lovable.
                    Although it started as a prototyping tool, its feature set and collaboration capabilities make it a suitable for production-adjacent \glsxtrshortpl{MVP}, internal tools and small applications \cite{medioum-choosing-ai-tools}.
                }
        \subsubsection*{Bolt.new}
            {
                    Bolt.new targets developers who want "prompt-to-full-stack" generation while retaining framework flexibility. 
                    It can scaffold applications across multiple stacks (React, Angular, Vue, React Native, etc.) and is backed by Supabase
                    for backend and database support, similar to Lovable.
                    Compared to Lovable, Bolt places more emphasis on exposing the underlying code and project structure, which provides greater control but also 
                    demands more debugging and configuration effort. 
                    It also supports working with real repositories and two-way GitHub sync. 
                    For teams that must target specific frameworks (for example, Angular or React Native), Bolt is a more natural fit than tools that assume React only, but its
                    \glsxtrshort{UX} is less polished for non-experts \cite{medioum-choosing-ai-tools}.
                }
        \subsubsection*{Figma Make}
            {
                    Figma Make is tightly integrated into the Figma ecosystem, a widely used collaborative design platform for creating high-fidelity \glsxtrshort{UX} layouts,
                    and is therefore particularly attractive to designers \cite{figma}.
                    It starts from high-fidelity UI layouts and turns them into interactive prototypes that closely match the original design.
                    This design-first approach is powerful for validating user flows and visual details with stakeholders. 
                    However, the generated code is harder to reuse outside Figma, and complexity grows quickly once custom logic and structure are layered on top.
                    Although Figma Make supports backend integration (e.g., via Supabase), its current strength lies in rich prototypes rather than production-ready application code.
                    For teams already working with Figma, its cost overhead is low, but they must be prepared  to deal with frequent minor bugs and inconsistencies \cite{medioum-choosing-ai-tools}.
            }

        \subsection*{Summary}
            {
                \textit{Vibe Coding} tools such as Lovable, Bolt.new, and Figma Make complement traditional AI code assistants by operating at the level of full components
                and applications, which can dramatically reduce the time between a textual requirement and a testable interface, as summarized in Table~\ref{tab:vibe_coding_tools__comparison}. 
                At the same time, their focus on speed means that generated code requires refactoring to fit a layered architecture, careful handling of security
                and vendor lock-in, and conventional testing before institutional deployment. 
                For this project, these tools are therefore used as accelerators to bootstrap React-based prototypes that are later stabilized in a hand-curated codebase.  
            }

                \centering

\section{Summary and Justification of Technological Choices}
    {
        The preceding sections surveyed alternative technologies for the backend, data persistence layer, frontend frameworks, and \glsxtrshort{AI}-assisted development.
        This subsection summarizes and justifies the concrete choices adopted for the platform, in light of the requirements and constraints identified in Chapter~\ref{cha:requirements_and_system_analysis}.
    }

    \subsection{Backend Architecture}
        {
            Section~\ref{sec:sota_backend} compared \gls{BaaS} solutions with custom backend built with mature frameworks such as Spring Boot and Express.js. 
            \gls{BaaS} platforms like Supabase are particularly attractive for early-stage projects because they provide read-made infrastructure
            for authentication, storage, and real-time \glsxtrshortpl{API}, enabling rapid prototyping with small teams.
        }

        {
            For this project, Supabase will be used in the initial phase to support \glsxtrshort{AI}-assisted, \textit{Vibe Coding}-driven prototyping of the core workflows.
            However, the long-term target architecture is a custom backend implemented with Spring Boot. 
            This choice is justified by:
        }
        \begin{itemize}
            \item {the need to code complex domain logic (student seriation rules, audit policies) with strong typing and explicit layering;}
            \item {the importance of testability and maintainability for an institutional system that is expected to evolve over multiple editions;}
            \item {the need to integrate cleanly with PostgreSQL features such as \gls{RLS} and LISTEN/NOTIFY}
        \end{itemize}
        {
            In practice, the prototype built on Supabase is evolved rather than discarded: the data model and \glsxtrshort{API} contracts defined during
            prototyping are reused by the Spring Boot backend, minimizing migration effort.
        }
    \subsection{Data Persistence}
        {
            Section~\ref{sec:sota_data_persitance} contrasted relational (\glsxtrshort{SQL}) and non-relational (\glsxtrshort{NoSQL}) database models. 
            Relational database prioritize integrity and consistency through \glsxtrshort{ACID} guarantees and referential constraints, while
            \glsxtrshort{NoSQL} systems offer schema flexibility and horizontal scalability at the cost of weaker consistency.
        }
        
        {
            Given the structured nature of the problem domain-editions, students, companies, proposals, applications, and protocols - and the critical
            importance of correctness in operations such as seriation and assignments, a relational model is more appropriate. \\
            The expected scale (bounded by the number of students and companies in the department) does not require the extreme horizontal
            scalability that motivates most \glsxtrshort{NoSQL} deployments.
        }
        
        {
            PostgreSQL is therefore adopted as the primary data store because it:
        }
        \begin{itemize}
            \item {enforces referential integrity between core entities, preventing impossible states such
                as assignments to non-existent proposals or inactive companies
            ;}
            \item {
                supports \gls{RLS}, which is essential for enforcing multi-tenant access rules directly at the database layer;
            }
            \item {
                provides \glsxtrshort{JSON}/\glsxtrshort{JSONB} columns for semi-structured data (\textit{e.g.,} email templates, feedback metadata), allowing 
                limited schema flexibility without introducing a separate \glsxtrshort{NoSQL} system.
            }
        \end{itemize}

    \subsection{Frontend Frameworks and Styling}
        {
            Section~\ref{sec:sota_frontend} compared React and Angular as representative frontend technologies. 
            In this project, React is chosen as the primary \glsxtrshort{UI} technology for two main reasons:
        }
        \begin{itemize}
            \item {
                its component-based model fits the need to offer multiple role-specific dashboards built from reusable components;
                }
            \item {
                it algins closely with the \textit{Vibe Coding} tools used in the prototyping phase, which predominantly
                generate React Frontends
            }
        \end{itemize}

        {
            Next.js can be adopted around React when needed, main to provide routing and flexible rendering strategies (\glsxtrshort{SSR}, \glsxtrshort{SSG}, \glsxtrshort{ISR})
            for pages that benefit from server-side or static rendering, without changing the underlying React component model. 
            This combination supports both rapid prototyping and a clear path to production-ready, performance interfaces.
        }

    \subsection{AI-Assisted Development (\textit{Vibe Coding})}
        {
            Section~\ref{sec:sota_ai_assited_dev} introduced \textit{Vibe Coding} tools such as Lovable, Bolt.new and Figma Make, which influence the development workflow
            but are not part of the runtime architecture. In this project these tools will be used to bootstrap React/Supabase prototypes
            and to generate much of the initial \glsxtrshort{UI} and \glsxtrshort{CRUD} logic for core workflows, or to convert high-fidelity
            Figma designs into React components that can be integrated into the main code base
            
            These tools are not part of the runtime 
            architecture of the platform, but they strongly influence the development workflow.
        }
        
        {
            Generated code is treated as a starting point: it is refactored into a layered architecture and combined with a 
            Spring Boot + PostgreSQL backend where critical concerns such as the data model, security, seriation logic, and auditing
            are implemented and reviewed. 
            In this way, \textit{Vibe Coding} accelerates time-to-prototype and exploration of alternatives, while the final institutional platform
            converges on a conventional, maintainable stack.
        }
