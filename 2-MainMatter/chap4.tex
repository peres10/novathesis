\section{Proposed System Architecture}
\label{sec:sol_architecture}
\ntindex[Template]{}
    {
        The proposed platform follows a three-layer architecture that separates user interface, application logic and data persistence, 
        as illustrated in Figure~\ref{fig:Figure_Architecture_Diagram}.
        This layered structure follows established practice for web applications of this kind and is particularly appropriate here 
        because it simplifies maintenance and allows the platform incrementally, 
        without forcing disruptive changes to the overall design.
    }
    % raquel sequeira silva
    {
        At the presentation layer, a React-based web application delivers role-specific dashboards for students, company representatives, professors, coordinators, and the secretariat.
        The \glsxtrshort{UI} will be composed of reusable components for common views, which simplifies maintaining consistent behavior and visual language across roles.
        For student authentication, the platform will integrate with the university's identity provider using OAuth, so that students
        can log in with their institutional accounts and their profile and enrollment information can be imported without manual registration.
    
    }

    {
        The application layer exposes a REST \glsxtrshort{API} that encapsulates all business logic. 
        During the initial prototyping phase, this layer can rely on managed services (such as Supabase) for basic authentication
        and \glsxtrshort{CRUD} operations, so that core workflows can be validated quickly with real users.
        As the system stabilizes, a Spring Boot-based backend assumes responsibility for the domain logic.
    }

    {
        The data layer is implemented with PostgreSQL, using a relational schema such as the one described in Section~\ref{sec:sol_erd}.
        Referential integrity is enforced with foreign keys to prevent inconsistent states, and \gls{RLS} is used to constrain which rows each role can access.
        External services complement this layer, as shown in Figure~\ref{fig:Figure_Architecture_Diagram}: a transactional email provider is used for reliable delivery and tracking of notifications, and an object storage
        service holds upload documents such as CVs, protocols and reports. 
    }

    {
        Together, these elements allow \glsxtrshort{AI}-assisted prototypes to be refined into a secure, maintainable platform rather than being discarded.
    }

\section{Process Modelling (BPMN)}
\label{sec:sol_bpmn}
\ntindex[Template]{}
    {
        To complement the textual use case model and clarify the most critical workflows, three \glsxtrshort{BPMN} diagrams were
        created and included in the Appendix~\ref{ann:bpmn_appendix} (Figures~\ref{fig:BPMN1}-\ref{fig:BPMN3}). These models focus on the processes that generate most of the coordination
        effort in the system: company registration, proposals submission and validation, and student seriation and assignments.
        They are intentionally simple and somewhat "raw", serving as a first iteration that captures main actors, decisions,
        and state transitions without yet modelling every possible exception or alternate path.
    }

    {
        The first diagram (Figure~\ref{fig:BPMN1}) describes the registration of a company representative and the creation or association
        of a company entity in the platform. 
        It shows how an employee accesses an external registration page, submits personal details, and either selects
        and existing company, or creates a new one, while the system validates input, stores employee and company data,
        and sends verification e-mails.
    }

    {
        The second diagram (Figure~\ref{fig:BPMN2}) models the proposal submission and validation workflow for companies and professors.
        It begins when the submitter enters an open edition, fills in the proposal form, and decides whether to save a draft
        or submit; the system then saves the proposal and notifies coordinators that a new item is pending validation.
        On the coordinator side the diagram highlights the three main outcomes - accept, reject or request clarifications - 
        together with the corresponding status transitions and notifications, matching the feedback loop defined in the requirements.
    }

    {
        The third diagram (Figure~\ref{fig:BPMN3}) covers the seriation and assignment process across students, coordinators, companies/professors,
        and the system. 
        It starts with students registering in an edition and ranking proposals, followed by the coordinator triggering
        seriation and the system computing assignments, with different mapping rules for undergraduate internships 
        (one student to zero or one internship) and Master's dissertation (one student to zero or more themes).
        The diagram then shows notifications to students and submitters, interview and confirmation steps on the
        company/professor side, and iterative seriation runs when assignments are not confirmed, or there are still students
        without any assignments.
    }

    {
        Overall, these \glsxtrshort{BPMN} models do not attempt to exhaustively represent every alternative or error condition but instead
        provide a high-level, visual view of the core lifecycle processes that drive the platform's requirements and architecture.
        They will be refined in future iterations as the implementation uncovers additional edge cases and 
        as coordinators and other stakeholders provide feedback on real usage. 
    }

\section{Data Model (ERD)}
\label{sec:sol_erd}
\ntindex[Template]{}
    {
        The data model for the platform is organized around a relational schema that reflects the main actors, academic structures, and workflows
        identified in the requirements and use cases, it is summarized in the \gls{ERD} presented in Appendix~\ref{ann:bpmn_erd} (Figure~\ref{fig:ERD1}).
        At the core of the schema is the \textit{User} entity, which stores generic account information (name, e-mail, status, creation date)
        and is linked to \textit{UserRole} and \textit{UserRoleAssingment} so that a single user can accumulate multiple roles over time 
        (for example, a professor who is also an edition coordinator). 
        Specialized profiles such as \textit{Student}, \textit{Professor}, and \textit{CompanyEmployee} extend \textit{User} with domain-specific attributes:
        \textit{Student} references academic data and supporting files (CV, image),
        \textit{Professor} holds scientific field and contact details, and \textit{CompanyEmployee} ties a user to a specific \textit{Company} and optional department.
    }

    {
        The academic context is structured around \textit{Edition}, which represents an internship or dissertation cycle and is complemented by
        \textit{EditionDates} (key deadlines and milestones) and associative tables such as \textit{EditionProposal}, \textit{EditionStudent}, \textit{EditionCoordinator},
        while preserving edition-specific configuration (deadlines, capacity limits, coordinator assignments), and supports
        functional requirements such as per-edition proposals limits and the distinction between undergraduate internships and Master's
        dissertations.
        Companies are modelled with a \textit{Company} entity that can reference a parent company (to represent groups or departments), a responsible
        employee, and an \textit{Address}, which together provide the structure needed for validation and communication between the \gls{DI} and companies.
    }

    {
        The core lifecycle of proposals and applications is captured by \textit{Proposal}, \textit{Application}, and \textit{Assig}.
        \textit{Proposal} stores the main attributes of an internship or dissertation theme, including submitter links (company or professor)
        and an optional \textit{ProposalPreviousAgreement} sub-entity for cases where a student and/or a professor already have an informal agreement.
        \textit{Application} links a \textit{Student}, \textit{Proposal}, and \textit{Edition}, with preference rank and timestamps, while \textit{Assignment} records the outcome of 
        seriation and later decisions (status and audit timestamps), aligning with the use cases for ranking, seriation, and assignment.
        Communication and feedback are handled by \textit{Interaction} and \textit{ProposalFeedback}, which represent messages between actors, their metadata
        (author, destination, type, attachments), and whether a proposal was updated after feedback, providing traceability required for auditability,
        and iterative refinement.
    }

    {
        Cross-cutting concerns are supported by a small set of utility entities. \textit{File} and \textit{Image} provide a generic mechanism to store metadata
        for uploaded documents and images (CVs, protocols, profile pictures), while \textit{StudentAcademicData} keeps academic data of students (\glsxtrshort{ECTS}, average grade)
        used by the seriation algorithm without embedding this logic directly into core entities.
        Foreign keys and many-to-many association tables enforce referential integrity and reject business relationships (for example,
        students participating in multiple editions, proposals reused across editions), while the relational model remains flexible enough to evolve 
        as additional requirements and entities are refined beyond this initial \glsxtrshort{ERD}.
        
    }

\section{Work Plan}
\label{sec:sol_workplan}
\ntindex[Template]{}
    {
        The work plan follows the iterative methodology outline in Section~\ref{sec:intro_methodology}, mapping its main phases on the period from 
        March to September. 
        The schedule is organized so that early months already include hands-on prototyping, middle months focus on hardening the architecture and 
        implementing core workflows, and the last month emphasizes thesis writing and final validation, with overlapping activities across phases.
    }
    {
        \subsection*{Planned phases and timing (by month)}
            \begin{itemize}
                \item { 
                    {\textbf{March} - Environment setup and initial prototyping}
                    \begin{itemize}
                        \item {
                            Build an initial React/Supabase prototype with Vibe Coding tools for core flows such as company registration, proposal submission, and 
                            basic student interaction, aiming to keep this within a few weeks.
                        }
                        \item {
                            In parallel, refine and, when needed, adjust the existing requirements, use case specifications, BPMN diagrams, and ERD based on both feedback
                            and needs from the first prototype.
                        }
                        \item {
                            Set up the development environment structure, and basic \glsxtrshort{CI} routines for frontend, backend and database.
                        }
                    \end{itemize}
                }
                \item {
                    {\textbf{April} - Expanding Prototype Coverage and early Spring Boot backend}
                    \begin{itemize}
                        \item {
                            Extend the prototype to cover additional workflows: student ranking, basic seriation logic, and simple notification flows
                            backed by Supabase.
                        }
                        \item {
                            Align the PostgreSQL schema with the ERD, including creation of tables, constraints, and initial \gls{RLS} rules that reflect the role model.
                        }
                        \item {
                            Start introducing a Spring Boot backend in parallel for selected core use cases (e.g., proposal validation and feedback loop), preparing the gradual
                            migration away from Supabase-only backend.
                        }
                    \end{itemize}
                }
                \item {
                    {\textbf{May} - Backend consolidation and integration}
                    \begin{itemize}
                        \item {
                            Expand the Spring Boot backend to cover the main business logic (proposal lifecycle, seriation, user and company management) while progressively
                            reducing reliance on Supabase functionalities.
                        }
                        \item {
                            Define and implement REST API endpoints and integrate OAuth-based authentication with the university identity provider for student login.
                        }
                        \item {
                            Introduce structured audit logging and improve notification handling, ensuring consistency with architecture in Figure~\ref{fig:Figure_Architecture_Diagram}
                        }
                    \end{itemize}
                }
                \item {
                    {\textbf{June} - Implementation of Core Workflows and hardening}
                    \begin{itemize}
                        \item {
                            Complete the main end-to-end workflows (submission, validation, clarification, candidacies, seriation, basic protocol management)
                            using the Spring Boot backend and PostgreSQL schema.
                        }
                        \item {
                            Refine the ERD and database schema based on usage and performance observations (indexes, additional constraints, small structural adjustments).
                        }
                        \item {
                            Expand automated testing (unit/integration tests) and conduct targeted non-functional checks (performance of critical queries, RLS correctness).
                        }
                    \end{itemize}
                }
                \item {
                    {\textbf{July} - Advanced Features, Integration and Optimization}
                    \begin{itemize}
                        \item {
                            Implement remainings such as per-edition company proposal limits, export capabilities, improved admin tools (superuser supports, configuration screens),
                            feedback on companies.
                        }
                        \item {
                            Optimize the performance of key dashboards and API calls and reinforce security aspects (\glsxtrshort{RBAC} enforcement, audit coverage, error handling for edge cases).
                        }
                        \item {
                            Reserve a short vacation period starting at the end July and continuing into early August, limiting work during that window to minor fixes
                            or small tasks that do not block later phases.
                        }
                    \end{itemize}
                }
                \item {
                    {\textbf{August} - Validation, evaluation and documentation consolidation}
                    \begin{itemize}
                        \item {
                            Perform more systematic validation against the functional and non-functional requirements in Appendix~\ref{ann:fr_nfr_appendix},
                            including seriation correctness, email deliverability, usability and auditability. 
                        }
                        \item {
                            Collect structured feedback from stakeholders on the platform and prioritize any feasible adjustments within the remaining schedule.
                        }
                        \item {
                            Consolidate technical documentation (architecture, APIs, data model, deployment notes) and ensure that BPMN and ERD diagrams reflect the implemented system.
                        }
                    \end{itemize}
                }
                \item {
                    {\textbf{September} - Thesis Writing and Final Adjustments}
                    \begin{itemize}
                        \item {
                            Focus primarily on writing and finalizing the dissertation document, while reserving limited time for minor fixes or polish to the platform if necessary.
                        }
                    \end{itemize}
                }
            \end{itemize}
    }
